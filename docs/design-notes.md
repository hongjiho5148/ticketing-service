## 설계 포인트

"기능을 넣었다"보다 **"깨질 수 있는 지점을 어떻게 막았는가"** 를 기준으로 정리했습니다.

| 문제 | 해결 |
|---|---|
| 같은 좌석을 동시에 잡는 경쟁 | Redisson 분산락 + 좌석 상태 확인을 한 임계 구역에서 처리, 30건 동시 요청에도 중복 0건 |
| 같은 QR을 동시에 두 번 스캔 | `UPDATE … WHERE status='ISSUED'` 한 문장으로 전이해 한 건만 성공 |
| 쿠폰 사용 한도·포인트 잔액 경쟁 | 조건부 `UPDATE`(영향 행 수 확인)로 처리, 읽고-쓰기 방식 금지 |
| 결제는 됐는데 쿠폰/포인트 차감이 실패 | 결제 금액·상태를 PortOne 서버에 다시 조회해 검증한 뒤 차감하고, 실패하면 자동 환불 후 주문 실패 처리 |
| 환불 구간이 확인 중에 바뀜 | 화면에 보여준 환불액을 서버로 되돌려 보내 달라지면 거절(`REFUND_QUOTE_CHANGED`) |
| 취소와 양도가 동시에 들어옴 | 주문 행 비관적 락 + 한 주문에 수락 대기 양도 1건만(유니크 제약) |
| 양도 수락/거절/취소가 겹침 | 상태 전이를 조건부 `UPDATE` 한 문장으로 처리해 먼저 온 한 건만 반영 |
| 관리자 토큰이 일반 사이트에서 쓰임 | 관리자 앱·토큰 저장소·로그인 분리, 관리자 토큰은 15분 단명, 일반/소셜 로그인은 관리자 계정을 거부 |
| 봇의 로그인 대입·좌석 선점 | IP별 레이트 리미팅 + 로그인/대기열 진입 캡차(검증 서버 장애 시 통과시키지 않음) |
| 시크릿이 소스에 박혀 토큰 위조 가능 | JWT·QR 시크릿 기본값 제거, 없거나 32바이트 미만이면 서비스 기동 거부 |
| 메일 서버가 느리거나 죽음 | 메일은 커밋 이후 비동기 발송(스레드풀 제한), 실패는 로그만 남기고 본 흐름 유지 |
| 중복 알림/폭주 | 취소표 알림은 좌석 1개당 최대 3명(오래된 순), 선점 `UPDATE`로 중복 발송 방지 |

## 부하테스트로 검증한 것들

설계가 "될 것 같다"가 아니라 "작동한다"는 걸 k6(1000 VU 기준) 부하테스트로 직접 증명했습니다.

| 검증 항목 | 이전 | 이후 |
|---|---|---|
| 서비스 분리(4차) 후 예약 API 지연(p95) | 122ms | 139ms (홉 1개 추가, 허용 범위로 판단) |
| 대규모 동시 요청 시 실패율 | 24% | **0.05%** (nginx 임시 포트 고갈 → 정적 업스트림+keepalive로 해결) |
| `backend` 3레플리카 요청 분산(30건 기준) | 30 : 0 : 0 (전혀 분산 안 됨) | 9 : 10 : 11 (내부 동적 로드밸런서 추가 후) |
| 좌석 중복 예약 | - | 30건 동시 요청에도 0건 |
| 부하테스트 중 발견한 설계 결함 | 취소된 좌석 1,003/5,460석이 영구 재예약 불가 | DB 유니크 제약 수정으로 전부 복구 |

자세한 과정은 [`docs/`](./docs)와 커밋 로그(`nginx 시작 안정성 + backend 로드밸런싱 수정`,
`nginx 커넥션 재사용 + 좌석 영구 재예약 불가 버그 수정` 등)에 남아 있습니다.

> 위 수치는 기능 확장(쿠폰·QR·알림·봇 방어 등) **이전 구조** 기준으로 측정한 값입니다. 이후 추가한 레이트 리미팅과 캡차는
> 부하 생성기 한 대를 한 IP로 보고 막기 때문에, 부하테스트를 다시 돌릴 때는 아래 "부하테스트 실행" 절처럼 끄고 실행해야 합니다.

### 부하테스트 실행

게이트웨이는 IP당 요청 수를 제한하고 대기열 진입에는 캡차가 걸려 있으므로([봇 방어](./architecture.md#봇-방어-레이트-리미팅) 참고), 부하 생성기 하나가 한 IP로 보이고 캡차를 풀 수 없는 부하테스트에서는 둘 다 끄고 돌립니다.

```bash
RATE_LIMIT_ENABLED=false CAPTCHA_ENABLED=false docker compose up -d gateway auth-service backend
docker run --network ticketing-service_default --ulimit nofile=200000:200000 \
  -e BASE_URL=http://nginx/api -v "$(pwd)/loadtest:/scripts" grafana/k6 run /scripts/reserve_flow.js
```

스크립트는 `loadtest1~50@example.com` 계정으로 로그인하고, 대기열 병목을 빼고 예약 파이프라인만 재려면 `QUEUE_ACTIVE_CAPACITY`를 크게,
`QUEUE_ADMISSION_INTERVAL_MS`를 짧게 올려서 backend를 띄웁니다.

### 재측정 (2026-10, 현재 구조)

기능을 확장한 뒤의 구조로 다시 쟀습니다(Windows 노트북의 Docker Desktop, **k6도 같은 PC**, 대상 공연 좌석 2,710석, 로그인 → 대기열 → 좌석 목록 → 예약 → 취소 반복).

| 조건 | 예약 p95 | 오류 |
|---|---|---|
| 1000 VU, 대기열 기본값(500명/300ms), backend 1개 | 2,472ms | 대기열 진입 502 3,820건 |
| 1000 VU, 대기열 해제, backend 3개 | 6,442ms | 없음 (409 좌석 충돌 2,374건은 정상) |
| 100 VU, 대기열 해제, backend 3개 | 571ms | 없음 |

- 위 "서비스 분리 후 예약 p95 139ms"와는 **같은 조건이 아니라서 직접 비교할 수 없고, 현재 구조에서는 재현되지 않았습니다.** 느려진 원인은 아직 분석하지 않았습니다.
- 확인된 병목: 대기열 상태 조회가 몰리면 nginx → backend 구간(동적 resolver라 keepalive 없음)에서 임시 포트가 고갈됩니다(`Address not available`). **→ 아래 "개선"에서 해결했습니다.**
- k6의 `http_req_failed`는 409(좌석 충돌, 락이 정상 동작한 결과)도 실패로 세므로, 오류율은 409를 뺀 값으로 봐야 합니다.

### 개선: nginx → backend 구간에 keepalive 적용 (2026-10)

**원인**: backend 경로는 `set $var http://backend:8080; proxy_pass $var;` 방식이라 요청마다 DNS를 다시 조회해 레플리카에 분산되지만, 이 방식은 연결을 재사용(pooling)하지 못해 **요청마다 새 TCP 연결**을 엽니다. 대기열 상태 조회가 초당 1,000건 안팎으로 몰리면 임시 포트가 바닥나 연결이 실패했습니다.

**해결**: upstream 그룹에 `server backend:8080 resolve;`(오픈소스 nginx 1.27.3부터 지원)와 `keepalive 64`를 함께 설정했습니다. 5초마다 다시 조회해서 레플리카 변화를 따라가면서(동적 발견) 연결은 풀로 재사용합니다. 요청별 어느 레플리카로 갔는지 `$upstream_addr`를 로그에 남겨 분산을 로그로 확인할 수 있게 했습니다.

**검증** — 같은 PC에서 변경 전후를 연달아, 같은 k6 스크립트(1000 VU, 대기열 기본값 500명/300ms, backend 1개), 각각 사용 이력이 없는 새 공연(대기열 상태가 겹치지 않도록)으로 측정:

| 지표 | 변경 전 | 변경 후 |
|---|---|---|
| 실패율 (`http_req_failed`) | 25.37% (15,828 / 62,382) | **0.04%** (63 / 154,125, 이 중 62건은 409) |
| 임시 포트 고갈 에러 (`Address not available`) | 15,745건 | **0건** |
| 대기열 진입 실패 | 2,169건 | 0건 |
| 처리량 | 647 req/s | **1,624 req/s** |
| 전체 HTTP p95 | 2.41s | **715ms** |
| 예약 API p95 | 3,576ms | 2,900ms |

- 레플리카 분산: backend 3개로 늘린 뒤 61건 요청이 **20 / 20 / 21** 로 고르게 갔고, 1개로 줄인 뒤 40건이 502 없이 남은 1개로만 갔습니다(동적 발견 유지 확인).
- **아직 남은 문제**: 예약 API p95가 2.9초로 여전히 높습니다(임계값 1.5초 초과). 이 지연은 nginx 연결 문제가 아니라 예약 경로에서 나오는 것으로, 아래 "예약 API 지연 분석"에서 원인을 좁혔습니다.
- 측정 환경 한계: 같은 PC에서 k6와 서버를 함께 돌렸고, 측정 중 다른 프로젝트의 컨테이너도 떠 있었습니다. 변경 전후는 같은 조건에서 연달아 측정했지만 절대값은 환경에 따라 달라집니다.
- 부수 발견: 대기열은 **폴링을 멈춘(이탈한) 대기자도 순번을 차지**하고 입장 슬롯까지 받습니다. 입장권(passToken)은 10분간 유지되어, 이탈자가 많으면 실제 사용자가 대기하는 시간이 길어집니다. 대기자 heartbeat/만료가 필요합니다(개선 과제).

### 예약 API 지연 분석 (2026-10)

nginx 문제를 고친 뒤에도 예약 API p95가 2~3초였습니다. 가설을 하나씩 실험으로 확인했습니다(1000 VU가 아니라 300 VU, 좌석 2,710석 공연, 대기열 해제, **설정마다 워밍업 1회를 버리고 3회 측정**).

| 확인한 것 | 결과 |
|---|---|
| 좌석이 296석뿐인 공연에 300명 | 좌석 락 경합(대기 500ms 후 409)으로 p95가 2.7초까지 올라감 → **테스트 설계 문제**였고, 좌석 2,710석 공연에서는 훨씬 낮음 |
| SQL 로깅(`show-sql`)이 초당 1만 줄 출력 | 끄고 재도 **지연은 거의 그대로**(평균 1.76s → 1.70s). 로그 폭주는 맞지만 원인은 아님 |
| JVM 워밍업 | 재시작 직후 첫 실행은 항상 약 2배 느림 → 워밍업 실행을 버려야 비교가 됨 |
| 동시 사용자 수별 지연 (평균) | 1명 40ms → 10명 56ms → 50명 191ms → 100명 371ms. 약 10명을 넘으면 지연이 동시 접속에 거의 비례하고 처리량은 30~45건/초에서 포화 |
| DB 연결 상태 | 서비스당 연결 10개(Hikari 기본값)가 모두 사용 중이고, 상당수가 `COMMIT` 대기 상태(`waiting for handler commit`) |
| 커밋 fsync | 내구성 설정을 완화(`innodb_flush_log_at_trx_commit=2`, `sync_binlog=0`)해도 개선은 작음 → 주원인 아님 |

**구조적으로 고친 것** (`perf/reservation-latency`):
- reservation-service의 `reserve()`/`cancel()`이 클래스 전체 `@Transactional`이라, **HTTP 호출(event-service, 대기열) 3번 동안 DB 연결을 붙잡고** 있었습니다. 트랜잭션을 걷어내 연결을 쓰는 순간에만 빌리게 했고, 저장 실패 시 좌석을 즉시 반납(보상)하도록 했습니다.
- event-service의 `hold()`는 트랜잭션 안에서 Redis 락을 기다려(최대 500ms) 연결을 잡고 있었고, 락이 커밋보다 먼저 풀렸습니다. **락을 먼저 잡고 그 안에서 짧은 트랜잭션**을 열도록 바꿔, 연결은 DB 작업 동안만 쓰고 커밋 후에 락이 풀리게 했습니다(`@Version`은 안전망으로 유지).
- SQL 로깅은 기본값을 끄고(`JPA_SHOW_SQL=true`로 켬) 로그 폭주를 막았습니다.

**전후 비교** (300 VU, 워밍업 후 3회 평균, 예약 API):

| 구성 | 평균 | p95 |
|---|---|---|
| 변경 전 기본값 (풀 10, SQL 로그 ON) | 1.76s | 2.84s |
| 변경 전 코드 + 풀 50 + SQL 로그 OFF | 0.80s | 1.48s |
| **변경 후 코드, 풀 10** | **1.10s** | **2.41s** |
| 변경 후 코드, 풀 20 | 1.12s | 2.17s |
| 변경 후 코드, 풀 50 | 1.12s | 2.30s |

- 해석: 변경 후 코드는 기본 풀(10)로도 기본값 대비 평균 약 **37% 낮은** 지연을 냈고, 풀을 키워도 추가 이득이 일정하지 않았습니다(**측정 편차가 ±0.2초 정도라 풀 크기별 차이는 노이즈 수준**). 변경 전 코드는 풀을 50으로 키워야 비슷한 수준이었으므로, 연결을 늘리지 않고도 같은 효과를 얻은 셈입니다.
- **한계**: p95는 여전히 2초대로 임계값(1.5초)을 넘고, 남은 병목은 특정하지 못했습니다. 같은 PC에서 k6와 서버가 돌고 다른 프로젝트 컨테이너도 떠 있어 환경 편차가 큽니다. 위 표의 값은 이 환경 기준의 상대 비교로만 읽어야 합니다.
- **분석 중 발견한 위험 → 수정함**: 예약 만료를 reservation-service와 event-service가 각자 정리하는데, `release(seatId)`가 소유자 확인 없이 좌석을 풀기 때문에, 한쪽이 먼저 풀고 다른 사용자가 홀드한 뒤 다른 쪽 스윕이 늦게 돌면 새 사용자의 홀드를 풀어 버릴 수 있었습니다. 아래 "좌석 해제 소유 확인"에서 고쳤습니다.

### 좌석 해제 소유 확인 (2026-10)

**문제**: 좌석 해제를 요청하는 쪽이 여럿입니다(사용자 취소, 결제 실패 보상, reservation-service 만료 스윕, event-service 만료 스윕). 해제 API가 "누구의 홀드인지" 확인하지 않아서, **늦게 도착한 해제 요청이 그 사이 같은 좌석을 홀드한 다른 사용자의 홀드를 풀 수 있었습니다**(이후 세 번째 사용자가 같은 좌석을 홀드하면 중복 예약 가능).

**해결**: 해제 요청에 그 홀드의 `holdExpireAt`을 함께 보내고, event-service는 **좌석이 아직 정확히 그 홀드 상태일 때만** 풀고 아니면 아무것도 하지 않습니다(`Seat.isHeldWith`). 홀드 만료 시각이 홀드의 신원 역할을 합니다(같은 좌석을 다시 홀드하려면 먼저 해제돼야 하고 그 사이는 1ms보다 훨씬 길므로 서로 다른 홀드가 같은 값이 될 수 없음, 서비스별 DB가 소수 초를 반올림하므로 1ms 허용 오차). 본문 없는 기존 호출은 무조건 해제로 남겨 호환을 유지했고, 낙관적 락 충돌은 "이미 다른 쪽이 바꿨다"로 보고 무시합니다.

**검증**: 실제 MySQL/Redis 통합 테스트 5개 — 지난 홀더의 늦은 해제가 새 홀더를 풀지 못함, 토큰 없는 해제는 기존대로 동작, 이미 판매된 좌석은 해제되지 않음, 이미 빈 좌석 해제는 무해, 서로 다른 반올림 값도 일치. (event-service 테스트 24 → 29개)

**남은 것**: `sell`(결제 확정)에 같은 확인을 아래 "결제 시 홀드 확인"에서 추가했습니다.

### 결제 시 홀드 확인 (2026-10)

**문제** (코드로 추적): 결제창이 열려 있는 동안 5분 홀드가 만료돼도 `pay()`는 홀드가 아직 유효한지 보지 않았고, 예약 확정(`confirm`)과 좌석 판매(`sell`)는 무조건 실행됐습니다. 그 사이 다른 사용자가 같은 좌석을 홀드하면 늦은 결제가 그 좌석을 팔아 버리고, 그 사용자도 결제하면 **한 좌석에 PAID 주문이 둘** 생길 수 있었습니다(QR 입장권도 두 장).

**해결** — 판매를 홀드에 묶었습니다:
1. event-service `sell(seatId, holdExpireAt)`: 좌석 락 안에서 **좌석이 아직 정확히 그 홀드일 때만** 판매하고, 아니면 `SEAT_HOLD_LOST`(410)를 던집니다. 같은 홀드로 이미 판매된 좌석에 다시 요청하면 조용히 성공(결제 재시도 대비). 이를 위해 판매 후에도 `holdExpireAt`을 "어느 홀드로 팔렸는지" 기록으로 남깁니다(만료 정리는 HOLD 상태만 대상이라 영향 없음).
2. reservation-service `confirm`: 홀드가 살아 있는(HOLDING) 예약만 확정하고, 만료·취소된 예약은 `HOLD_EXPIRED`(410). 이미 확정된 예약에 다시 요청하면 그대로 성공(멱등).
3. order-service `pay()`: 확정이 `HOLD_EXPIRED`로 실패하면 **쿠폰·포인트·적립을 전부 되돌리고 결제를 자동 환불**한 뒤 주문을 실패 처리하고, 응답에 `failureReason: HOLD_EXPIRED`를 담아 화면이 "예약 시간이 지나 결제가 자동으로 환불됐어요"라고 안내합니다. 다른 이유의 실패(예: reservation-service 장애)는 좌석을 잃었다는 증거가 없으므로 주문을 PENDING으로 두고 **같은 결제 id로 재시도**할 수 있게 합니다(환불하지 않음).

**검증**: 실제 MySQL/Redis 통합 테스트 — 좌석 판매 보호 6개(정상 판매, 다른 사용자가 홀드 중인 좌석·빈 좌석·다른 사용자에게 팔린 좌석은 판매 거부, 같은 홀드로 두 번 판매는 무해, 토큰 없는 호출은 기존대로), 예약 확정 4개(만료·취소 예약 거부와 좌석 미접촉, 중복 확정 무해), 결제 3개(정상 결제는 환불 없음, 홀드 만료 시 환불+주문 실패+예약 취소, 일시 장애는 환불 없이 PENDING 유지). event 29 → 35, reservation 3 → 7, order 53 → 56개.

**아직 남은 것**: `pay()`의 트랜잭션 범위는 아래 "결제 처리의 트랜잭션 범위 축소"에서 정리했습니다. (결제는 됐는데 `pay()`가 호출되지 않는 경우는 "결제 id 서버 발급과 대사 스윕"에서 다룹니다.)

### 결제 id 서버 발급과 대사 스윕 (2026-10)

**조사 중 발견한 보안 구멍**: 결제 id를 브라우저가 `randomUUID`로 만들고 서버는 그 id의 PortOne 결제가 "PAID이고 금액이 맞는지"만 확인했습니다. 결제 id가 **어느 주문의 것인지 묶여 있지 않아서**, 같은 금액의 PENDING 주문이 둘이면 **한 번 결제한 id로 두 주문을 모두 PAID로** 만들 수 있었습니다(`payment.order_id`는 유니크지만 `portone_payment_id`는 아니었음).

**해결 1 — 결제 id를 서버가 발급**: 결제창을 열기 전에 `POST /orders/{id}/payment-intent`로 `payment_attempt` 행(주문 id + 결제 id, 결제 id 유니크)을 만들고 그 id와 금액을 받아 결제창을 엽니다. `pay()`는 **그 주문에 발급된 id만** 받습니다(`PAYMENT_NOT_REGISTERED`). 금액도 서버가 정해서 내려줍니다.

**해결 2 — 대사(reconciliation) 스윕**: 결제는 됐는데 브라우저가 닫히거나 서버 호출이 계속 실패해 `pay()`가 끝나지 않은 주문을 1분마다 훑습니다(최근 60분 내 PENDING 주문만). 서버가 발급한 결제 id를 알기 때문에 PortOne에 직접 조회할 수 있게 된 것이 핵심입니다.
- 홀드가 아직 살아 있으면 건드리지 않습니다(고객이 `pay()`로 끝낼 수 있음).
- reservation-service에 닿지 않으면 **아무것도 하지 않습니다**(홀드가 살아 있는데 환불하는 쪽이 더 나쁨).
- 홀드가 끝났고 PortOne에 PAID가 있으면: 예약이 이미 확정(좌석 판매 후 커밋 실패)이면 주문을 **완료**하고, 아니면 **전액 환불 + 결제 기록(환불액) 저장 + 주문 실패 + 예약 취소**.
- 환불이 실패하면 PENDING으로 두어 다음 주기에 재시도하고, 계속 실패하면 로그(`AUTO-REFUND FAILED`)로 수동 환불 대상임을 남깁니다.

**검증**: 실제 MySQL 통합 테스트 13개 — 결제 id(서버 금액, 매번 새 id, 발급 안 된 id 거부, **다른 주문의 id 거부**, 남의 주문 거부)와 대사(환불, 만료 시각이 지난 HOLDING도 만료로 간주, 홀드 살아 있으면 무접촉, 예약 서비스 불통 시 무동작, 결제 안 된 시도 무시, 결제창을 안 연 주문 무조회, 좌석이 팔렸으면 주문 완료, 환불 실패 시 PENDING 유지). order-service 56 → 69개.

**미구현·한계**: 웹훅은 공개 주소가 필요해 대사 스윕으로 대신했습니다(최대 약 1분 지연). 실제 PortOne으로는 검증하지 못했고(모킹), 하나의 결제 id를 여러 시도에 재사용했을 때 PortOne의 동작은 확인하지 않아 시도마다 새 id를 발급합니다. 이미 결제를 시작한 구버전 프론트가 열려 있으면 `PAYMENT_NOT_REGISTERED`로 거부되므로 배포 시 프론트와 함께 올려야 합니다.

### 결제 처리의 트랜잭션 범위 축소 (2026-10)

**문제**: `OrderService`가 클래스 전체 `@Transactional`이라 `pay()`가 PortOne 조회, 예약 확정(reservation-service) 같은 **네트워크 호출 동안 DB 연결을 붙잡고** 있었습니다(앞서 예약 경로에서 고친 것과 같은 유형). 결제가 몰리면 연결 풀(기본 10개)이 네트워크 대기로 소진됩니다.

**해결**: `pay()`를 짧은 트랜잭션들로 쪼개고 그 사이의 네트워크 호출은 연결 없이 실행합니다.

| 단계 | 트랜잭션 |
|---|---|
| 주문·본인확인·결제 id 검증 | 짧은 읽기 트랜잭션 |
| PortOne 결제 조회 | **없음** |
| 쿠폰·포인트 차감 | 짧은 트랜잭션 |
| 예약 확정(좌석 판매) | **없음** |
| 주문 PAID 처리 + 결제 기록 | 짧은 트랜잭션 (주문 행 잠금) |

쪼개면 "중간에 실패했을 때 어디까지 되어 있는가"가 문제가 되므로 보완했습니다:
- **차감을 멱등하게**: 주문에 `benefits_redeemed_at` 표시를 두어(차감과 같은 트랜잭션에서 기록, 되돌릴 때 해제) 재시도가 쿠폰·포인트를 두 번 쓰지 못하게 했습니다.
- **좌석 확정이 실패하면 보상**: 이미 커밋된 쿠폰·포인트·적립을 되돌려 주문을 시도 전 상태로 만든 뒤, 홀드 만료면 환불, 일시 장애면 같은 결제 id로 재시도하게 합니다. (전에는 한 트랜잭션이라 예외 시 자동 롤백됐던 부분)
- **마지막 단계는 행 잠금 + 상태 확인**: 두 곳(고객 요청과 대사 스윕)이 동시에 완료하려 해도 한 번만 성공합니다.
- 대사 스윕도 같은 방식으로 PortOne·예약 서비스 호출 동안 연결을 잡지 않도록 바꿨습니다.

**검증**: 트랜잭션을 테스트가 감싸면 모든 호출이 "트랜잭션 안"이 되어 증명이 안 되므로, 이 두 테스트는 일부러 `@Transactional`이 아닌 실제 커밋 테스트로 작성하고 끝나면 행을 지웁니다.
- PortOne 호출과 예약 확정 호출이 실행되는 순간 **활성 트랜잭션이 없음**을 직접 확인(`TransactionSynchronizationManager`).
- 확정 실패 시 포인트가 정확히 원래대로 돌아가고, 재시도하면 한 번만 차감·적립, 홀드 만료 시 전부 원복, 차감을 두 번 호출해도 한 번만 반영.
- 기존 결제·대사·환불 테스트는 그대로 통과. order-service 69 → 73개.

**한계**: 차감 직후 서버가 비정상 종료하면 보상이 실행되지 않아 쿠폰·포인트가 차감된 PENDING 주문이 남을 수 있습니다(대사 스윕이 환불은 하지만 혜택 복구는 하지 않음). 이 경우 확정 호출이 성공하지 않았다면 같은 결제 id 재시도로 복구됩니다. 처리량 개선 효과는 부하 측정으로 확인하지 않았습니다(외부 PortOne 호출을 쓰는 경로라 로컬에서 재현 불가).

### 스키마 변경을 Flyway로 관리 (2026-10)

**문제**: 모든 서비스가 `ddl-auto: update`로, 기동할 때 Hibernate가 스키마를 코드에 맞췄습니다. 개발에서는 편하지만 운영에서는 위험합니다.
- 어떤 변경이 언제 DB에 들어갔는지 **기록이 없습니다.**
- `update`는 컬럼 추가만 하고 삭제·이름 변경·타입 변경은 하지 않아, 코드와 DB가 **조용히 어긋납니다.**
- 엔티티 오타 하나가 서비스를 띄우는 순간 곧바로 DB 변경이 됩니다.
- 서비스를 여러 대로 늘리면 인스턴스들이 동시에 스키마를 바꾸려 합니다.

**해결**: DB가 있는 5개 서비스(auth, event, reservation, order, backend)에 Flyway를 넣었습니다.
- `V1__baseline.sql`: Flyway를 넣을 때의 스키마(Hibernate가 만든 그대로)를 서비스별로 뽑아 기준선으로 두었습니다. 개발 DB를 덤프한 게 아니라, **빈 임시 MySQL에서 엔티티로 새로 생성한 스키마**를 썼습니다(개발 DB에 쌓인 옛 컬럼이 섞이지 않게).
- `ddl-auto: validate`: 엔티티와 DB가 다르면 **기동 단계에서 실패**합니다. 조용한 불일치 대신 바로 알게 됩니다.
- `baseline-on-migrate`: Flyway 이전에 만들어진 DB는 V1을 "이미 적용됨"으로 받아들이고, 빈 DB는 V1을 실행해 전부 만듭니다.
- 이후 스키마 변경은 `V2__설명.sql`처럼 **새 파일을 추가**합니다. 이미 적용된 파일을 고치면 체크섬이 달라져 기동이 막힙니다.

**검증**
- 빈 DB: 5개 서비스 모두 V1로 테이블이 생기고, `validate`를 통과하고, `flyway_schema_history`에 기록됨.
- 기존 개발 DB: 5개 모두 V1이 `BASELINE`으로 기록되고 기동 성공. DB를 쓰는 5개 서비스의 JUnit 테스트 138개가 그대로 전부 통과(gateway 12개는 변경 없음).

**한계**: V1은 "그 시점 Hibernate가 만든 스키마"를 복원한 것이라 그 전의 변경 이력은 없습니다. 오픈소스 Flyway는 되돌리기(undo)를 지원하지 않아 롤백 스크립트가 없습니다. 운영 데이터가 있는 DB에서 마이그레이션을 돌려 본 적은 없고(로컬 개발 DB만), 서비스 여러 대가 동시에 기동하는 경우의 잠금 동작도 따로 확인하지 않았습니다.

### 좌석 목록 읽기 최적화 (2026-10)

**문제**: 좌석 목록(`GET /events/{id}/seats`)은 공연의 모든 좌석을 한 번에 돌려줍니다(2,712석 공연 기준 응답 약 360KB). 공연 페이지를 열 때마다 불리고, 예약 흐름 부하테스트에서는 매 반복마다 받아서 수신량의 대부분이 이 응답이었습니다. 공연 상세 조회도 좌석 요약을 내려고 그 공연의 좌석 엔티티를 전부 읽어 메모리에서 세고 있었습니다.

**측정 방법**: 좌석 목록만 반복 조회하는 `loadtest/seat_list.js`(200 VU, 30초, 2,712석 공연). 단계마다 **첫 실행(워밍업)을 버리고 3회 평균**, 같은 PC에서 k6와 서버를 함께 돌렸고, 게이트웨이 레이트 리미팅은 측정 동안만 껐습니다(끝나고 복원).

| 단계 | 처리량 | 평균 지연 | p95 | 요청당 응답 크기 | event-service CPU |
|---|---|---|---|---|---|
| 변경 전 | 299 req/s | 604ms | 1.25s | 약 360KB | 약 490% |
| ① 쿼리 최적화 | 466 req/s | 251ms | 695ms | 약 360KB | 약 387% |
| ② ① + nginx 1초 캐시 (압축 안 받는 클라이언트) | 988 req/s | 70ms | 441ms | 약 360KB | 약 2% |
| ③ ② + gzip (브라우저처럼 압축 허용) | 745 req/s | 109ms (중앙값 29ms) | 714ms | **약 29KB** | 약 8% |

**한 일**
1. **쿼리 최적화**: 좌석 목록을 엔티티가 아니라 응답 레코드로 바로 읽도록(projection) 바꿔, 좌석 수천 개의 엔티티 생성·변경 감지 비용을 없앴습니다. 공연 상세의 좌석 요약은 DB의 `GROUP BY`로 셉니다. 응답 모양과 순서(id 순)는 그대로입니다.
2. **nginx 1초 캐시**: 좌석 목록 경로만, 모든 방문자에게 같은 응답이므로 1초 동안 캐시합니다. 캐시가 비는 순간 몰린 요청은 `proxy_cache_lock`으로 한 건만 upstream에 보내고, upstream이 실패하면 오래된 응답을 대신 내줍니다. 인증 정보와 상관없는 공개 응답이라 URL(`?grade=` 포함)로만 구분합니다.
3. **gzip**: 같은 JSON 키가 반복되어 360KB가 약 28KB로 줄어듭니다(요청당 약 92% 감소). 압축 레벨은 1로 두었습니다(레벨 4는 바이트가 7%만 더 줄고 CPU는 더 씁니다).

**시도했다가 되돌린 것**: event-service가 한 번만 압축하고 nginx가 압축본을 그대로 캐시하게 해서 nginx의 압축 CPU를 없애려 했습니다. 그런데 event-service에 직접 요청하면 압축되어 오는데 gateway를 거치면 압축이 풀린 채(360KB) 도착했습니다. 원인은 확인하지 못했고, gateway의 HTTP 클라이언트 동작을 건드리는 건 이 변경의 범위를 넘어서 되돌렸습니다.

**테스트**: 이 두 경로에는 테스트가 없었습니다. `SeatListTest` 5개로 목록(모든 상태의 좌석, id 순, 등급 필터, 없는 공연), 상세 요약(등급·구역별 합계와 "가능" 개수, 좌석 없는 공연)을 확인합니다. event-service 35 → 40개.

**한계**
- 가장 큰 효과는 event-service의 부하가 거의 사라진 것(CPU 약 490% → 약 8%)입니다. **p95는 ③이 ①보다 나아지지 않았습니다**(714ms 대 695ms). 같은 PC에서 nginx의 압축(약 2.2코어)과 k6가 CPU를 나눠 쓰기 때문이라고 보지만, 다른 머신에서 재측정해 확인하지는 않았습니다. 평균과 중앙값은 크게 줄었습니다(604 → 109ms, 581 → 29ms).
- 목록이 **최대 1초 오래된** 채로 보일 수 있습니다. 방금 잡힌 좌석이 잠깐 "가능"으로 보일 수 있고, 그 좌석을 누르면 서버가 판정해 409로 거절합니다(좌석을 잡는 일 자체는 캐시와 무관).
- 공연 상세의 `GROUP BY` 변경은 따로 측정하지 않았습니다(구조적 개선으로만 주장).
- 좌석마다 같은 키와 값이 반복되는 응답 구조는 그대로입니다. 더 줄이려면 구역별로 묶거나 변하지 않는 배치와 자주 변하는 상태를 나누는 등 프론트엔드 변경이 필요합니다(다음 후보).
- nginx 캐시는 nginx 한 대 기준입니다. 여러 대로 늘리면 대수만큼 upstream 요청이 늘어납니다.

### Kafka 이벤트를 Outbox로 발행 (2026-10)

**문제**: 예약이 만들어지면 reservation-service가 `reservation.created`를 Kafka로 보냈습니다. 요청 스레드가 막히지 않도록 작은 스레드 풀에서 비동기로 보냈는데, 풀이 밀리면 이벤트를 **버렸습니다**(`DiscardPolicy`). 예약은 DB에 저장됐는데 이벤트는 사라질 수 있는 구조였고, Kafka가 잠깐 죽어 있던 시간의 이벤트는 되살릴 방법이 없었습니다. "DB에 저장"과 "Kafka에 발행"은 서로 다른 시스템이라 한 번에 둘 다 성공시킬 수 없습니다(이중 쓰기 문제).

**해결 (Transactional Outbox)**
- `reserve()`가 예약과 `outbox_event` 행을 **한 트랜잭션**에서 저장합니다. 둘 다 저장되거나 둘 다 안 됩니다. 예약 요청 경로에서 Kafka 호출이 사라졌습니다.
- `OutboxRelay`가 0.5초마다 아직 안 보낸 행을 id 순으로 읽어 Kafka로 보내고, **브로커가 받았다고 확인한 뒤에** `sent_at`을 기록합니다. 실패하면 그 행에서 멈춰 뒤의 이벤트가 앞지르지 못하게 하고, 가져간 행을 돌려놓아 다음 주기에 이어서 보냅니다.
- **여러 인스턴스가 같은 행을 두 번 보내지 않도록** 보내기 전에 행을 짧게 "임대(claim)"합니다. 한 번의 짧은 DB 트랜잭션에서 `SELECT … FOR UPDATE SKIP LOCKED`로 잠그고 임대 표시(`claimed_by`, `claimed_until`)를 한 뒤 커밋하고, 그다음에 Kafka로 보냅니다. 임대한 인스턴스가 죽으면 30초 뒤 임대가 끝나 다른 인스턴스가 이어받습니다.
- 예약이 커밋된 직후 릴레이를 바로 깨워(`kick`) 이벤트가 폴링을 기다리지 않고 수 ms 안에 나가게 했습니다. 깨우기를 놓쳐도 폴링이 안전망입니다.
- `OutboxRecorder`는 트랜잭션이 이미 열려 있어야만 동작합니다(`MANDATORY`). 트랜잭션 밖에서 호출되면 "저장은 됐는데 발행은 안 될 수 있는" 문제가 되살아나므로 거절합니다.
- 보낸 행은 24시간 뒤 지우고, 안 보낸 행은 지우지 않습니다. 릴레이가 Kafka 장애를 기다리는 동안 다른 스윕이 밀리지 않도록 스케줄러 스레드를 3개로 늘렸습니다.
- 장애 중에는 30초에 한 번, **가장 오래 기다린 이벤트가 몇 초째 대기 중인지**와 대기 건수를 경고로 남깁니다(알림을 걸 때 보는 숫자).
- 소비자(backend)는 처리하지 못하는 메시지를 1초 간격으로 3번 다시 시도한 뒤 `reservation.created.DLT`로 옮깁니다. 이 설정이 없으면 프레임워크 기본값은 로그만 남기고 건너뜁니다(메시지 유실).
- 테이블은 Flyway `V2`, `V3`(임대 컬럼)로 추가했습니다.

**동시성 테스트가 잡아낸 문제**: 처음에는 임대를 `UPDATE … ORDER BY id LIMIT 100` 한 문장으로 했는데, 여러 릴레이를 동시에 돌리는 테스트에서 "mark sent" 업데이트와 **교착(deadlock)** 이 났습니다. 두 문장이 인덱스와 기본 키를 서로 다른 순서로 잠그기 때문입니다. 이미 잠긴 행은 기다리지 않고 건너뛰는 `SKIP LOCKED`와, 갭 락을 잡지 않는 `READ COMMITTED` 트랜잭션으로 바꿔서 해결했고, 같은 테스트를 4번 연속 통과시켰습니다.

**검증**
- 테스트 11개 추가(reservation 7 → 18): 기록한 순서대로 보내고 보냄 표시, 이미 보낸 것은 다시 안 보냄, 브로커 실패 시 순서 유지·복구 뒤 이어서 발송, 예약과 이벤트가 함께 저장됨, **이벤트 기록이 실패하면 예약도 롤백되고 이미 잡은 좌석은 반납**, 트랜잭션 밖 기록 거절, 오래된 "보낸" 행만 삭제, **릴레이 4개가 동시에 돌아도 120건이 각각 정확히 한 번씩만 전송**, 다른 폴링이 임대 중인 행은 건드리지 않고 임대가 끝난 행은 이어받음, 커밋된 이벤트는 폴링을 기다리지 않고 전송, 롤백된 이벤트는 전송되지 않음.
- 실제 Kafka로 장애 재현: Kafka를 멈추고 outbox에 이벤트를 쌓음 → 전부 미발송으로 남고 릴레이가 재시도(경고는 30초에 한 번, 가장 오래 기다린 이벤트의 대기 시간 포함) → Kafka 재시작 → 순서대로 전송되고 backend가 같은 순서로 수신. 읽을 수 없는 메시지를 넣으면 DLT에 1건이 쌓이고, 그 뒤의 정상 이벤트는 계속 수신됨.

**예약 저장 경로의 비용** (`reserve()` 한 번, 원격 호출과 Kafka는 모킹, 8스레드 × 500회, 워밍업 제외, 같은 PC, 새 MySQL):

| | 평균 | p50 | p95 | p99 |
|---|---|---|---|---|
| 변경 전 (main, 3회 중앙값) | 8.1ms | 7.7ms | 11.9ms | 16.2ms |
| 변경 후 (5회 중앙값) | 10.3ms | 9.5ms | 16.3ms | 28.3ms |
| 변경 후, 커밋 직후 깨우기 끔 (3회 중앙값) | 10.0ms | 9.4ms | 15.4ms | 23.4ms |

**약 2ms(평균 기준 약 25%) 느려졌습니다.** 원인은 예약 저장에 `outbox_event` INSERT 한 건이 같은 트랜잭션에 더해졌기 때문이고, 커밋 직후 깨우기는 거의 영향이 없었습니다(끄면 10.0ms). 대신 이벤트 유실 가능성과 Kafka에 묶인 지연(과거 측정에서 최대 1~3초)이 없어졌습니다. 실제 요청은 다른 서비스 호출 3번이 더 들어가서 이 2ms의 비중은 작겠지만, 전체 흐름(E2E)으로는 재지 않았습니다.

**한계**
- 폴링 간격이 0.5초라, 커밋 직후 깨우기를 놓치면(재시작, 다른 인스턴스가 기록한 행) 최대 약 0.5초 늦게 나갑니다.
- 전달은 최소 한 번입니다. 보낸 직후 표시하기 전에 죽거나, 느린 전송이 임대(30초)보다 오래 걸리면 한 번 더 나갈 수 있습니다. 서로 다른 폴링이 가져간 행은 순서가 바뀔 수 있어서(지금은 이벤트마다 키가 달라 문제 없음) 같은 키의 이벤트가 여러 개 생기면 따로 설계해야 합니다.
- 인스턴스를 실제로 여러 대 띄워 보지는 않았고, 같은 DB에 여러 스레드(별도 연결)로 동시에 접근하는 테스트로 확인했습니다.
- 적체 상한은 없고(DB에 쌓임), 알림은 로그 경고뿐입니다. 지표를 내보내고 알림을 거는 일은 모니터링을 붙일 때 같이 합니다.
- 지금 소비자는 로그만 남깁니다. 이번 변경은 "이벤트가 유실 없이 도착한다"까지이고, 업무에 쓰는 소비자는 다음 단계입니다.
- 예약 저장 경로는 약 2ms 느려졌고 E2E 영향은 재지 않았습니다.

**운영 메모: DLT 메시지 다시 처리하기** (원인을 고친 뒤). 먼저 무엇이 왜 실패했는지 봅니다(헤더에 예외 이유가 있음):
```bash
docker exec ticketing-kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic reservation.created.DLT --from-beginning --timeout-ms 5000 --property print.headers=true
```
고친 뒤에는 DLT를 컨슈머 그룹으로 읽어 원래 토픽에 다시 넣습니다. 그룹 오프셋이 남으므로 **같은 메시지를 두 번 다시 넣지 않습니다**(두 번 실행해도 새로 늘어나지 않는 것을 확인함):
```bash
docker exec ticketing-kafka sh -c '/opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic reservation.created.DLT --group dlt-replay --consumer-property auto.offset.reset=earliest \
  --timeout-ms 6000 --property print.key=true --property key.separator="<탭>" 2>/dev/null \
  | /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic reservation.created \
  --property parse.key=true --property key.separator="<탭>"'
```
(`<탭>`은 실제 탭 문자입니다. 키가 없던 메시지는 키가 문자열 `null`로 들어가지만, outbox 이벤트는 항상 키가 있습니다. 다시 넣은 메시지는 중복 처리될 수 있으니 소비자는 중복을 견뎌야 합니다.)

### 구매를 마친 사람의 대기열 슬롯 반환 (2026-10)

**문제**: 대기열에서 입장한 사람은 "활성 슬롯"(동시에 입장할 수 있는 인원, 기본 500)을 하나 차지하고, 입장권(passToken)은 10분간 유지됩니다. 구매를 끝낸 사람도 슬롯을 10분 동안 쥐고 있어서, 줄이 길수록 뒤의 사람이 필요 이상으로 오래 기다립니다. 슬롯은 입장권이 만료될 때에만 돌아왔습니다.

**해결**
- 결제가 끝나 예약이 확정되면 reservation-service가 `reservation.confirmed` 이벤트를 outbox로 발행합니다. 확정과 같은 트랜잭션에서 기록하고, 확정이 되풀이돼도(결제 재시도) 이벤트는 예약당 한 번만 나갑니다.
- backend의 리스너가 이를 받아 구매한 사람의 활성 슬롯을 돌려줍니다. 입장 처리 타이머(0.3초)가 빈 슬롯에 다음 대기자를 바로 넣습니다.
- 대기열 키는 큐 토큰인데 결제 쪽은 그것을 모르므로, 이력 테이블에서 (사용자, 공연)으로 토큰을 찾습니다. 이력 테이블은 큐에 들어올 때마다 행이 쌓이므로 `(user_id, event_id)` 인덱스를 Flyway V2로 추가했습니다.
- 같은 메시지가 두 번 도착해도(최소 한 번 전달) 이미 돌려준 슬롯은 "없을 뿐"이라 아무 일도 일어나지 않습니다(멱등). 읽을 수 없는 메시지는 재시도 뒤 DLT로 가고, 그 뒤의 정상 메시지는 계속 처리됩니다.
- `queue.release-slot-on-purchase=false`로 끌 수 있습니다.

**바뀌는 동작**: 결제를 마친 사람의 입장권은 더 이상 유효하지 않아, 같은 공연의 좌석을 더 사려면 다시 줄을 서야 합니다. 결제 *전에* 좌석 여러 개(최대 4석)를 잡는 것은 그대로입니다. 예약 취소나 홀드 만료에는 슬롯을 돌려주지 않습니다(취소하고 다른 좌석을 고르는 사람이 많아서 입장권을 유지).

**시뮬레이션이 잡아낸 문제**: 처음에는 이력 행의 상태가 `PASSED`인 항목만 찾아 슬롯을 돌려주게 만들었는데, 시뮬레이션에서 **반환을 켰는데도 효과가 전혀 없었습니다**(152.5초 대 152.5초). 원인은 기존 코드에 있었습니다. `QueueAdmissionSweeper`가 입장 처리 때 이력 행을 `PASSED`로 바꾸는 `@Transactional` 메서드를 **같은 클래스 안에서 직접 호출**해서, 스프링 프록시를 거치지 않아 트랜잭션이 열리지 않고 그 변경이 저장되지 않았습니다. 단위 테스트는 테스트 전체가 하나의 트랜잭션이라 이 문제가 가려졌습니다. 이력 상태를 보지 않고 활성 슬롯 집합에 있는 토큰만 지우도록 바꾸고, 프록시를 거치지 않고 입장시키는 방식으로 실제 경로를 재현하는 회귀 테스트를 추가했습니다. (이력 행이 저장되지 않는 기존 문제 자체는 아래 "입장 이력이 저장되지 않던 문제"에서 따로 고쳤습니다.)

**검증**
- 테스트 11개 추가(backend 6 → 14, reservation 18 → 21): 구매자의 슬롯만 돌려받고 다른 사람과 다른 공연의 슬롯은 그대로, 돌려받은 슬롯에 다음 대기자가 입장, 두 번 받아도 무해, 끄면 유지, 확정 이벤트가 구매자와 공연을 담아 한 번만 기록됨, 확정할 수 없는 예약은 이벤트 없음, **실제 Kafka로 확정 메시지를 보내면 리스너가 슬롯을 돌려줌**(같은 메시지를 다시 보내도 무해, 읽을 수 없는 메시지 뒤의 정상 메시지도 처리).
- 대기 시간 시뮬레이션(실제 대기열·입장 타이머·리스너·Kafka, 새 MySQL·Redis): 60명이 동시에 줄을 서고, 동시 입장 10명, 입장권 30초(실제 10분을 줄인 값), 입장 후 3초 뒤 구매 완료 메시지(입장권 수명의 10%).

| | 전원 입장까지 | 대기 시간 p50 | 대기 시간 p95 |
|---|---|---|---|
| 슬롯 반환 없음 (기존) | 152.5초 | 91.8초 | 152.4초 |
| 구매하면 반환 (2회) | 21.4~21.7초 | 14.2~14.5초 | 21.4~21.7초 |

약 7배 빨라졌습니다. 이론값(60명 ÷ 10명 × 3초 = 18초)에 가깝습니다.

**한계**
- 이득은 "입장권 수명 ÷ 구매에 걸리는 시간"에서 나옵니다. 위 표는 그 비율이 10배이고 **모든 사람이 구매하는 최선의 경우**입니다. 실제 구매 소요 시간의 분포는 측정하지 않았습니다.
- **줄에서 이탈하거나 구매하지 않는 사람은 그대로 입장권이 만료될 때까지 슬롯을 차지합니다.** 이탈자 문제는 이 변경으로 풀리지 않고, 폴링이 끊기면 슬롯을 돌려받는 방식(heartbeat)이 따로 필요합니다(미구현).
- 이벤트가 지연되거나 유실되면 슬롯은 원래대로 입장권이 만료될 때 돌아옵니다(안전망).

### 입장 이력이 저장되지 않던 문제 (2026-10)

**문제**: `QueueAdmissionSweeper.admitForEvent`는 `@Transactional`이었지만 같은 클래스의 `admitWaitingUsers()`가 **자기 자신을 직접 호출**해서 스프링 프록시가 끼어들지 못했고, 트랜잭션이 열리지 않았습니다. 그 안에서 `findByQueueToken(...).ifPresent(WaitingQueue::pass)`로 엔티티를 읽어 바꿨지만 저장되지 않아, 실제로 돌아가는 서비스에서는 `waiting_queue` 이력 행이 **영원히 `WAITING`** 이었습니다(`passed_at`도 비어 있음). Redis의 입장 처리 자체는 정상이었고, 이력(통계)만 틀렸습니다. 기존 테스트는 테스트 전체가 하나의 트랜잭션이라 이 문제가 가려졌습니다.

**해결**: 입장 처리 때 한 번의 벌크 UPDATE로 바꿨습니다. 리포지토리의 `markPassed(tokens, now)`가 `update WaitingQueue set status=PASSED, passedAt=:now where queueToken in :tokens and status=WAITING` 한 문장을 실행합니다. `@Transactional`은 리포지토리 메서드에 붙였고(리포지토리 호출은 프록시를 거침), 호출하는 쪽에 트랜잭션이 있든 없든 동작합니다. `admitForEvent`의 `@Transactional`은 거짓 안심을 주므로 뺐습니다. 이력은 통계일 뿐이므로 DB 오류가 나도 Redis에서 이미 입장시킨 사람은 그대로 두고 경고만 남기며 다음 공연으로 넘어갑니다.

**쓰기 부하 측정** (한 번의 입장 처리로 500명, 실제 MySQL, Hibernate 통계로 SQL 개수 집계, 같은 JVM에서 두 방식을 번갈아 3회씩, 각 방식의 첫 회(2.1초 / 159ms)는 워밍업이라 제외):

| | SQL | 소요 시간 (워밍업 이후) |
|---|---|---|
| 사람마다 SELECT + UPDATE (엔티티 변경) | 1,000문장 | 약 0.5~0.8초 |
| 벌크 UPDATE | 1문장 | 약 16~20ms |

사람마다 처리하는 방식은 입장 타이머 주기(0.3초)보다 오래 걸리고 DB 왕복이 500~1000번이라 바로 탈락시켰고, 벌크 UPDATE를 택했습니다. `queue_token`의 유니크 인덱스로 행을 찾으므로 풀 스캔이 아니고, 한 번에 갱신하는 행 수는 빈 슬롯 수(최대 `queue.active-capacity`)로 제한됩니다. 정상 상태에서는 슬롯이 나는 만큼만 입장시키므로 틱당 갱신 행은 훨씬 적습니다. 원래 코드는 이 SELECT 500번이 이미 발생하고 있었던(저장만 안 되던) 비용이어서, 오히려 수정 후 DB 왕복이 줄었습니다.

**테스트**(backend 14 → 16): 일부러 `@Transactional`을 붙이지 않은 `QueueAdmissionHistoryTest`가 실제 타이머가 부르는 `admitWaitingUsers()`를 호출한 뒤 커밋된 행을 읽습니다. 입장한 5명은 `PASSED`와 `passed_at`이 채워지고 대기 중인 1명은 `WAITING` 그대로이며, 슬롯이 나면 다음 사람이 `PASSED`가 됩니다. 수정 전 코드로 되돌려 두 테스트가 `expected: PASSED but was: WAITING`으로 실패하는 것을 확인했습니다. 슬롯 반환 리스너 테스트가 "이력이 `WAITING`으로 남는다"를 단언하던 부분은 `PASSED`로 바꿨습니다.

**알려진 점**
- 수정 전에 입장한 이력 행은 `WAITING`으로 남아 있습니다(과거 통계는 복구하지 않음). 그래서 슬롯 반환은 여전히 이력 상태를 보지 않고 활성 슬롯 집합만 봅니다.
- 같은 로직이 다른 곳에도 있는지(`this.` 호출되는 `@Transactional`)는 이번에 backend의 큐 패키지만 확인했습니다.
- Kafka 리스너 테스트는 스프링 컨텍스트가 하나 늘어날 때마다(컨슈머가 같은 그룹에 하나 더 붙음) 파티션 할당이 늦어져 10초 대기 제한에 걸릴 수 있습니다. 새 테스트를 같은 컨텍스트 설정으로 맞춰 컨텍스트를 늘리지 않았고, 근본적으로는 리스너 테스트가 자기 컨슈머 그룹을 쓰게 하는 편이 낫습니다(이번에는 손대지 않음).

### 서비스 간 호출의 타임아웃·서킷 브레이커·재시도 (2026-10)

**문제**: 서비스끼리 부르는 HTTP 클라이언트(예약→이벤트·대기열, 주문→이벤트·인증·예약, 이벤트→인증·주문, 대기열→이벤트)와 PortOne 클라이언트에 **타임아웃이 하나도 없었습니다**(`RestClient.builder().build()`). 게이트웨이가 서비스로 프록시할 때도 마찬가지였습니다(앞단 nginx가 60초에 포기). 연결은 받지만 응답하지 않는 서비스가 생기면 그 서비스를 부르는 모든 스레드가 끝없이 묶이고, 스레드가 바닥나면 호출한 쪽 서비스까지 멈춥니다(연쇄 장애). 캡차(3초)와 KOPIS만 타임아웃이 있었습니다.

**해결** (서비스 호출 한 곳을 `RemoteService`로 모음, 4개 서비스에 같은 구조)
- **타임아웃**: 연결 1초, 읽기 5초(PortOne 10초, 주문→예약 8초). 5초는 좌석 락 대기와 임대(3초)를 합쳐도 넘지 않는 값이라 정상 호출은 자르지 않고 멈춘 호출만 끊습니다. 주문→예약은 예약이 이벤트 서비스를 다시 부르므로(최대 5초) 그보다 길게 잡았습니다. 게이트웨이는 연결 2초·읽기 30초(관리자 KOPIS 가져오기가 가장 느린 정상 호출).
- **서킷 브레이커**(Resilience4j): 최근 30번의 호출 중 최소 10번이 쌓인 뒤 실패율(I/O 오류·타임아웃·5xx)이 50% 이상이면 10초간 호출 없이 바로 거절하고, 10초 뒤 3번만 시험 호출해 성공하면 닫습니다. 4xx(없음·충돌·만료)는 **서비스가 답한 것**이라 실패로 세지 않습니다. 열려 있을 때는 연결 거부와 같은 예외를 던지므로 기존 "서비스를 쓸 수 없음" 처리가 그대로 동작합니다.
- **재시도**: 반복해도 안전한 호출(조회, 이미 처리됐으면 일찍 돌아오는 확정·취소, 좌석 해제·판매는 홀드로 멱등)만 **한 번**, 연결 거부나 502/503처럼 **금방 실패하는 경우에만** 다시 합니다. 타임아웃은 재시도하지 않습니다(대기만 두 배가 됨). **좌석 홀드는 재시도하지 않습니다**(두 번째 홀드는 충돌로 보임). PortOne 환불은 재시도하지 않습니다(응답이 유실돼도 대사 스윕이 다시 확인).

**검증**
- 테스트 40개 추가(서비스마다 `RemoteServiceTest` 10개, 로컬 포트의 진짜 HTTP 서버 사용): 응답 없는 서버는 읽기 타임아웃에서 실패, 연결 거부는 즉시 실패, 실패가 쌓이면 서킷이 열려 서비스에 닿지 않고 거절, 서비스가 살아나면 닫힘, 404는 서킷에 영향 없음, 503은 멱등 호출만 한 번 재시도, 타임아웃은 재시도 안 함, 열린 서킷은 재시도 안 함. 4개 서비스 전체 테스트 통과(reservation 31 · backend 26 · event 50 · order 83).
- 응답하지 않는 서버를 호출하는 쪽에서 본 차이(같은 서버, 읽기 1초로 축소):

| | 이전(타임아웃 없음) | 이후 |
|---|---|---|
| 호출자 50명이 동시에 호출 | 10초 뒤에도 **50명 전원 대기 중** | 1.2초 만에 전원 해제 |
| 같은 호출 40번을 순차 실행 | 끝없이 대기 | 타임아웃만 40.1초 → +서킷 브레이커 **10.2초**(30번은 호출 없이 즉시 거절) |

- 실제 스택으로 장애 재현(`docker pause`로 event-service를 20초 동안 얼림, k6 100 VU 70초, main 이미지와 같은 조건으로 번갈아 측정, 새 공연으로 대기열 용량을 키워 실행):

| | 이전 (main) | 이후 |
|---|---|---|
| 10초 넘게 걸린 예약 요청 | 62건 | 0건 |
| 예약 응답 최대 | 22.0초 | 5.2초 |
| 예약 응답 p95 | 1,455ms | 809ms |
| 반복 1회 최대 / p95 | 23.1초 / 7.27초 | 15.3초 / 2.52초 |
| 예약 성공(201) | 3,206건 | 3,773건 |
| 실패 응답(`http_req_failed`) | 0.54% | 9.61% (장애 중 즉시 반환된 503) |

예약 서비스의 서킷은 얼린 지 5초 뒤에 열렸고, 얼림을 풀자 반쯤 열림을 거쳐 0.1초 만에 닫혔습니다(대기열 서비스도 같은 흐름). 정상 부하(400 VU 60초)에서는 서킷이 한 번도 열리지 않았고 예약 p95는 484ms였습니다.

**트레이드오프**: 이전에는 사용자가 20초 기다리면 풀린 뒤 **성공**했지만, 이후에는 장애 중에 **빨리 오류**를 받고 다시 시도해야 합니다(실패율이 높아 보이는 이유). 대신 서버의 스레드가 묶이지 않아 장애 중에도 다른 요청과 복구 직후 요청이 정상 처리됩니다.

**한계**
- 게이트웨이가 직접 프록시하는 경로(예: 좌석 목록·이벤트 조회)는 서킷 브레이커가 없고 30초 타임아웃뿐입니다. 타임아웃이 나면 응답이 502/504가 아니라 500으로 나옵니다.

- 서킷 상태는 인스턴스마다 따로입니다(공유하지 않음). 여러 대일 때 한 대만 열릴 수 있습니다.
- 상태 전이는 로그 경고로만 남습니다(지표·알림은 모니터링 단계).
- 대기열 서비스가 이벤트 서비스를 부르는 `getEvent`가 실패하면 입장 자체가 막힙니다(이전과 같은 의미지만 이제 빨리 실패).

## 알려진 한계

과장하지 않기 위해, 검증하지 못했거나 의도적으로 단순화한 부분을 적어둡니다.

- **PortOne 실결제는 검증하지 못했습니다.** 결제창 호출, 부분 취소, 간편결제 팝업은 실제 결제가 필요해 직접 돌려보지 않았고,
  환불 구간·쿠폰/포인트·자동 환불 로직은 통합 테스트로 검증했습니다.
- **본인확인은 스텁입니다.** 결제 전 "본인 명의로 결제합니다" 동의를 주문별로 기록할 뿐 신원을 증명하지는 않으며,
  `IdentityVerificationProvider` 구현체만 바꾸면 PASS 같은 실제 인증으로 교체할 수 있게 분리해 두었습니다.
- **KOPIS로 가져온 공연의 좌석·판매는 합성 데이터입니다.** 실제 공연의 예매가 아니며, 좌석 수는 가격대 수에 따라 고정 크기로 만듭니다.
  KOPIS는 공연예술만 다루므로 전시·스포츠 장르는 직접 등록해야 합니다.
- **이용약관·개인정보처리방침은 데모 서비스 기준의 초안**입니다. 실제 운영 시에는 법률 검토가 필요합니다. 회원 탈퇴·정보 삭제는
  화면 기능이 없고 문의하기 이메일로 받는 것으로 안내했습니다.
- **레이트 리미팅은 단일 게이트웨이 기준**(메모리)이고, 공유 IP 환경에서는 걸릴 수 있습니다.
- **쿠폰은 모두 공개 쿠폰입니다.** 사용 기간 안에 한도가 남은 쿠폰은 로그인한 누구에게나 목록에 보이고, 특정 사용자에게만 지급하는 쿠폰(쿠폰함·발급)은 없습니다.
- **인당 매수 제한은 동시 요청에서 1~2석 넘을 수 있습니다.** 집계와 홀드가 한 트랜잭션이 아니기 때문이며, 락으로 막는 대신 봇 방어와 함께 보완하는 쪽으로 남겨 두었습니다.
- **오픈 전 공연의 예약을 서버가 막지는 않습니다.** 화면에서 대기열 진입을 막고 오픈 시각이 지나면 상태를 자동 전환합니다.
- **알림 메일은 자동 재시도하지 않습니다.** 인증 메일은 재발송으로, 나머지는 로그로 확인합니다.
- **부하테스트 수치는 시점이 섞여 있습니다.** 처음의 24% → 0.05%는 기능 확장 이전 구조 기준이고, 현재 구조에서는 "재측정" 절에서 다시 쟀습니다(25.37% → 0.04%). 모든 측정은 같은 PC에서 k6와 서버를 함께 돌린 전후 비교용입니다.
- **DB 계정 등 로컬 기본값은 개발용**이라 실제 배포 전에는 환경변수로 분리해야 합니다(JWT·QR 시크릿은 이미 필수값).
- **좌석 목록은 최대 1초 오래될 수 있습니다**(nginx 캐시). 좌석을 잡는 일 자체는 서버가 판정하므로 오버셀과는 무관합니다.
- **Kafka 이벤트는 최소 한 번 전달**이라 중복될 수 있고, 소비자는 멱등해야 합니다. 현재 의미 있는 소비자는 `reservation.confirmed`(대기열 슬롯 반환)뿐이고, `reservation.created`는 로그만 남깁니다.
- **대기열에서 이탈하거나 구매하지 않는 사람은 입장권이 만료될 때까지 슬롯을 차지합니다.** 슬롯 반환은 구매를 마친 사람에게만 적용됩니다.
- **적체 알림·지표는 로그 경고뿐입니다.** 모니터링 도구와 CI/CD, 클라우드 배포는 없습니다.
