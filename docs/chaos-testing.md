# 장애 시험 (Chaos testing)

실제 사용자가 있다고 가정하고, **저장소나 서비스가 죽었을 때** 사용자가 무엇을 겪는지, 알림이 울리는지, 복구 후 데이터가 어긋나지 않는지를 확인하는 도구와 방법이다. 부하를 버티는 시험(k6 전후 비교)과는 목적이 다르다.

## 합격 기준

시험 전에 정해 두고, 보고서가 아래 4가지를 자동으로 판정한다.

| 기준 | 값 |
|---|---|
| 장애 중 오류를 빨리 받는다 | 실패 응답의 p95 지연 5초 이하(서버 스레드가 몇십 초씩 묶이지 않는다) |
| 알림이 울린다 | 장애 시작 후 60초 안에 기대한 알림이 울림 |
| 사람이 손대지 않아도 복구된다 | 장애 해제 후 60초 안에 오류율 1% 미만(10초 창) |
| 데이터가 어긋나지 않는다 | 시험 전에 없던 정합성 위반이 새로 생기지 않음 |

## 구성

| 파일 | 하는 일 |
|---|---|
| `scripts/chaos/run.mjs` | 한 번의 시험을 처음부터 끝까지 실행(점검, 기준선, 부하, 장애, 정합성, 보고서) |
| `scripts/chaos/inject.mjs` | 컨테이너에 장애를 넣고 되돌림. 시작·종료 시각을 기록. 끊겨도 반드시 복구 |
| `scripts/chaos/invariants.mjs` | 정합성 검사(읽기 전용). 시험 전 기준선에 없던 위반만 본다 |
| `scripts/chaos/report.mjs` | 결과 폴더에서 보고서(Markdown) 생성 |
| `scripts/chaos/compare.mjs` | 여러 시험을 한 표로 비교(요청/초, p95, 아웃박스 적체 등) |
| `scripts/chaos/chaos.test.mjs` | 위 계산 부분의 테스트 (`node --test scripts/chaos/chaos.test.mjs`) |
| `loadtest/chaos_flow.js` | 장애 시험용 부하(사용자 N명이 처음부터 끝까지 일정하게 줄 서기 → 예약 → 취소 반복) |

## 장애 방식

| mode | 하는 일 | 보는 것 |
|---|---|---|
| `stop` | `docker stop` 후 `start` | 정상 종료. Redis는 종료 전에 데이터를 저장함 |
| `kill` | `docker kill` 후 `start` | 강제 종료. Redis는 마지막 저장 이후 데이터를 잃을 수 있음(RDB 스냅샷만 씀) |
| `pause` | `docker pause` 후 `unpause` | 프로세스는 살아 있는데 응답이 없음. 멈춘 DB나 네트워크 단절에 가장 가깝다 |

대상: `mysql`, `redis`, `kafka`, `gateway`, `auth-service`, `event-service`, `reservation-service`, `order-service`, `backend`. 모니터링 컨테이너는 일부러 뺐다(지켜보는 쪽이 같이 죽으면 안 된다).

## 실행

부하 생성기 하나는 한 IP로 보이고 캡차를 풀 수 없으므로, 속도 제한과 캡차를 끄고 띄워야 한다. 실행기가 시작 전에 확인하고, 안 되어 있으면 아래 명령을 알려 주며 시작하지 않는다.

```bash
RATE_LIMIT_ENABLED=false CAPTCHA_ENABLED=false docker compose up -d gateway auth-service backend
```

서비스가 모두 기동할 때까지 1~2분 기다린 뒤:

```bash
# 점검만(장애도 부하도 없음)
node scripts/chaos/run.mjs --target redis --mode stop --preflight-only

# 한 번 실행(기본: 100명, 240초, 60초째에 장애, 30초 유지)
node scripts/chaos/run.mjs --target redis --mode stop --label redis-stop
```

결과는 `loadtest/results/<시각>-<이름>/`에 모인다(git에는 올리지 않는다). 가장 먼저 볼 것은 `report.md`다. 다시 만들려면 `node scripts/chaos/report.mjs --dir <폴더>`.

### 기준선과 부하 크기

장애 시험 전에 같은 부하를 장애 없이 한 번 돌려 정상 수치를 잡는다(`--baseline`). 정상 상태에서 알림이 울리거나 실패율이 1% 이상이면 "기준선으로 쓸 수 없음"이 나오고, 이유가 보고서에 적힌다. 알림이 이미 울리는 부하에서 장애를 넣으면 알림 감지 시간을 잴 수 없기 때문이다.

```bash
node scripts/chaos/run.mjs --baseline --users 50 --label baseline-50vu
```

이 PC에서는 100명이면 아웃박스가 밀려 `OutboxBacklog`가 울렸고(릴레이 일꾼을 늘려 줄였다, [`design-notes.md`](./design-notes.md#아웃박스-처리-속도-정상-부하에서도-이벤트가-몇-분씩-밀리던-문제-2026-11)), 50명은 알림 없이 깨끗했다. 장애 시험은 50명으로 한다.

여러 시험을 한 표로 비교하려면 `node scripts/chaos/compare.mjs <폴더> <폴더> ...`. 같은 100명이어도 시험마다 이벤트 생산량이 20~75/초로 달랐으므로(시스템이 느리면 덜 만들어지는 부하 방식), 전후 비교는 번갈아 여러 번 재고 밀릴 만큼 몰린 시험끼리 봐야 한다.

**장애가 알림 지연보다 짧으면 알림이 울리지 않는 것이 정상일 수 있다.** 저장소 다운 알림은 수집 5초 + 판정 5초 + 대기 10초라서 다운되고 최대 약 20초 뒤에 울린다. 그보다 짧은 장애(`--fault-for`)로는 "알림이 울린다" 기준을 판정할 수 없다. 처음 Redis 시험은 30초 장애인데 알림 지연이 약 30초여서 알림이 울리지 못했고(그것이 문제였다), 지금은 20초 안에 울린다.

**시험 중에는 PC가 잠자기에 들어가지 않게 해야 한다.** 한 번 잠들었다 깨면 k6와 서비스의 시계가 어긋나 그 시험은 무효가 된다(실제로 겪었다). 덮개를 닫거나 절전을 직접 선택하면 어떤 방지 수단도 소용없다.

장애를 넣은 채로 Ctrl+C로 끊으면 장애를 되돌리도록 만들었지만, Windows 터미널에서 실제로 끊어 본 시험은 아직 하지 않았다(정상 종료와 오류 경로의 복구는 일회용 컨테이너로 확인했다). 컨테이너가 멈춘 채 남았으면 `docker compose up -d`(멈춘 컨테이너), `docker unpause <이름>`(얼린 컨테이너)로 되살린다.

## 정합성 검사

| 검사 | 뜻 |
|---|---|
| 한 좌석에 살아 있는 예약이 둘 이상 | 좌석 중복 예약 |
| 한 좌석에 결제 완료 주문이 둘 이상 | 이중 판매 |
| SOLD 좌석인데 확정된 예약이 없음 | 좌석과 예약의 불일치 |
| HOLD 좌석인데 살아 있는 예약이 없음 | 좌석이 아무도 모르게 묶임 |
| 살아 있는 예약인데 좌석이 HOLD가 아님 | 예약은 있는데 좌석을 못 잡음 |
| 결제 완료 주문인데 예약이 확정되지 않음 | 결제만 되고 좌석이 없음 |
| 전송 안 된 아웃박스 이벤트 | Kafka로 나가지 못한 이벤트 |
| 대기열 입장 인원이 정원 초과 | 대기열 정원 위반 |

서비스가 비동기로 정리하는 것(홀드 만료 스윕, 1분마다 하는 결제 대사, 아웃박스)은 장애 직후 잠깐 어긋나 보일 수 있다. 그래서 장애 후 최대 120초 동안 반복 확인하고, **끝까지 남은 새 위반만** 문제로 센다. 처음에 있었지만 정리된 것은 "서비스가 스스로 복구했다"로 따로 기록한다.

이 PC의 DB에는 시험과 무관한 옛 데이터(예: 10월 초 손으로 넣은 주문 `reservation_id 990001~`)에서 나온 위반이 이미 있다. 그래서 "0건"이 아니라 시험 전 기준선과 비교한다.

## 한계

- 한 PC에서 docker 명령으로 흉내 낸 장애다. 실제 네트워크 단절, 지연, 부분 장애와는 다르다.
- 서버와 부하 생성기가 같은 PC의 자원을 나눠 쓴다. 절대값보다 구간끼리의 비교로 읽는다.
- 요청 타임아웃을 20초로 끊는다(`--req-timeout`). 실제 브라우저는 더 오래 기다릴 수 있다.
- k6와 Prometheus의 시각은 Docker VM 시계, 장애를 넣는 시각은 호스트 시계라서 시작 전에 둘의 차이를 재서 맞춘다. 오차는 약 ±1초다.
